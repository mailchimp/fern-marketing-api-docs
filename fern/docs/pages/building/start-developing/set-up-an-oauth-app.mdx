Developers building apps that access Marketing API data on behalf of Mailchimp
users use OAuth 2 for authentication and authorization.

OAuth 2 is an open web standard for authorization. To learn how Mailchimp's
OAuth 2 flow works and why it has the steps it does, see
[OAuth 2](/marketing/api-concepts/authentication/oauth-2).

<Note>
This page is for apps whose `client_id` starts with `prd_`, which every app
registered on or after **November 13, 2026** has. If your `client_id` doesn't
start with `prd_`, or your code sends users to `login.mailchimp.com`, see
[Legacy OAuth 2 apps](/marketing/api-concepts/authentication/legacy-oauth-2).
</Note>

## What you'll need

- A Mailchimp account for registering your application
- [An API key](/marketing/build/get-started/generate-your-api-key),
  if you want to test against your own account first
- A **redirect URI** for your application. This is the URL Mailchimp sends
  users back to after they authorize your application. It must be reachable by
  the user's browser, but for local development `http://127.0.0.1:3000/...` is
  fine.
- The scopes your application needs, such as `campaigns:read`. The
  [API reference](/marketing/api) lists the scopes each endpoint requires.

## Register your application

Registering gives you a `client_id` and a `client_secret`.

1. Navigate to the [**Registered Apps page**](https://us1.admin.mailchimp.com/account/oauth2/) in your Mailchimp account.
2. Click **Register An App**.
3. Fill out the **Register An App** form, using the fields below.
4. Click **Create**.

| Field | What to enter |
| --- | --- |
| App name | Shown to users on the login and consent screens. Up to 128 characters. |
| Redirect URIs | At least 1. All of them must share one registrable domain. Subdomains of that domain are allowed, but each URI must match exactly; wildcards aren't supported. |
| Scopes | Select every scope your app might request. Your app can never request a scope that isn't selected here. |

You'll see the `client_id` and `client_secret` at the bottom of the page. Store
the `client_secret` on your server, encrypted at rest or in a secrets manager.
Don't hash it: your app sends the secret itself to the token endpoint, so it
needs the original value. See
[Your application's credentials](/marketing/api-concepts/authentication/oauth-2#your-applications-credentials).

<Note>
This is the only time you'll be able to see `client_secret`, so copy it and
store it securely.
</Note>

Register a separate app for each environment, such as development, staging, and
production, so each has its own credentials.

## Implement the flow on your server

The samples below send the user to authorize with a PKCE challenge, check the
callback, and exchange the code for tokens. Pick your language.

<CodeBlocks>
```typescript title="TypeScript"
// Node 18+, npm install express
import express from "express";
import crypto from "node:crypto";

const ISSUER = "https://oauth.mailchimp.com";
const REDIRECT_URI = "http://127.0.0.1:3000/oauth/callback";
const { MC_CLIENT_ID: id, MC_CLIENT_SECRET: secret } = process.env;
const pending = new Map<string, string>(); // state -> code_verifier

const app = express();

// 1. Send the user to authorize, with a PKCE challenge
app.get("/auth", (_req, res) => {
  const state = crypto.randomBytes(16).toString("base64url");
  const verifier = crypto.randomBytes(48).toString("base64url");
  pending.set(state, verifier);
  res.redirect(`${ISSUER}/oauth2/authorize?` + new URLSearchParams({
    response_type: "code",
    client_id: id!,
    redirect_uri: REDIRECT_URI,
    scope: "campaigns:read",
    state,
    code_challenge: crypto.createHash("sha256").update(verifier).digest("base64url"),
    code_challenge_method: "S256",
  }));
});

// 2. Check state and iss, then exchange the code for tokens
app.get("/oauth/callback", async (req, res) => {
  const { code, state, iss } = req.query as Record<string, string>;
  const verifier = pending.get(state);
  pending.delete(state);
  if (!verifier || iss !== ISSUER) return res.sendStatus(400);

  const tokenRes = await fetch(`${ISSUER}/oauth2/token`, {
    method: "POST",
    headers: { Authorization: "Basic " + Buffer.from(`${id}:${secret}`).toString("base64") },
    body: new URLSearchParams({
      grant_type: "authorization_code",
      code,
      redirect_uri: REDIRECT_URI,
      code_verifier: verifier,
    }),
  });
  res.status(tokenRes.status).json(await tokenRes.json()); // store these in a real app
});

app.listen(3000);
```

```php title="PHP"
<?php
// php -S 127.0.0.1:3000 index.php
$id = getenv('MC_CLIENT_ID');
$secret = getenv('MC_CLIENT_SECRET');
$issuer = 'https://oauth.mailchimp.com';
$redirectUri = 'http://127.0.0.1:3000/oauth/callback';
session_start();

function b64url($bin) { return rtrim(strtr(base64_encode($bin), '+/', '-_'), '='); }

// 1. Send the user to authorize, with a PKCE challenge
if (isset($_GET['login'])) {
    $_SESSION['state'] = b64url(random_bytes(16));
    $_SESSION['verifier'] = b64url(random_bytes(48));
    header("Location: $issuer/oauth2/authorize?" . http_build_query([
        'response_type' => 'code',
        'client_id' => $id,
        'redirect_uri' => $redirectUri,
        'scope' => 'campaigns:read',
        'state' => $_SESSION['state'],
        'code_challenge' => b64url(hash('sha256', $_SESSION['verifier'], true)),
        'code_challenge_method' => 'S256',
    ]));
    exit;
}

// 2. Check state and iss, then exchange the code for tokens
if (isset($_GET['code'])) {
    $expected = $_SESSION['state'] ?? '';
    $verifier = $_SESSION['verifier'] ?? '';
    unset($_SESSION['state'], $_SESSION['verifier']);
    if ($expected === '' || !hash_equals($expected, $_GET['state'] ?? '') || ($_GET['iss'] ?? '') !== $issuer) {
        http_response_code(400);
        exit;
    }
    $ch = curl_init("$issuer/oauth2/token");
    curl_setopt_array($ch, [
        CURLOPT_RETURNTRANSFER => true,
        CURLOPT_USERPWD => "$id:$secret",
        CURLOPT_POSTFIELDS => http_build_query([
            'grant_type' => 'authorization_code',
            'code' => $_GET['code'],
            'redirect_uri' => $redirectUri,
            'code_verifier' => $verifier,
        ]),
    ]);
    echo curl_exec($ch); // store the tokens in a real app
}
```

```python title="Python"
# pip install flask requests
import base64, hashlib, os, secrets
from urllib.parse import urlencode

import requests
from flask import Flask, redirect, request

ISSUER = "https://oauth.mailchimp.com"
REDIRECT_URI = "http://127.0.0.1:3000/oauth/callback"
ID, SECRET = os.environ["MC_CLIENT_ID"], os.environ["MC_CLIENT_SECRET"]
pending = {}  # state -> code_verifier, kept on the server

app = Flask(__name__)

# 1. Send the user to authorize, with a PKCE challenge
@app.route("/auth")
def auth():
    state = secrets.token_urlsafe(16)
    verifier = secrets.token_urlsafe(48)
    pending[state] = verifier
    digest = hashlib.sha256(verifier.encode()).digest()
    return redirect(f"{ISSUER}/oauth2/authorize?" + urlencode({
        "response_type": "code",
        "client_id": ID,
        "redirect_uri": REDIRECT_URI,
        "scope": "campaigns:read",
        "state": state,
        "code_challenge": base64.urlsafe_b64encode(digest).rstrip(b"=").decode(),
        "code_challenge_method": "S256",
    }))

# 2. Check state and iss, then exchange the code for tokens
@app.route("/oauth/callback")
def callback():
    verifier = pending.pop(request.args.get("state", ""), None)
    if not verifier or request.args.get("iss") != ISSUER:
        return "", 400
    res = requests.post(f"{ISSUER}/oauth2/token", auth=(ID, SECRET), data={
        "grant_type": "authorization_code",
        "code": request.args["code"],
        "redirect_uri": REDIRECT_URI,
        "code_verifier": verifier,
    })
    return res.json(), res.status_code  # store the tokens in a real app

app.run(port=3000)
```

described in

If the user denies access, or the request is invalid, the callback arrives with
an `error` query parameter instead of a `code`. See
[Errors](/marketing/api-concepts/authentication/oauth-2#errors).

### The flow step by step

To build the flow in another language or framework, follow these steps. They're
what the samples above do.

1. Generate a `code_verifier`: a random string of 43 to 128 characters from
   `A-Z a-z 0-9 - . _ ~`. Make a new one for every authorization and keep it on
   your server.
2. Compute `code_challenge` as `BASE64URL(SHA256(code_verifier))`, with no `=`
   padding.
3. Redirect the user to `/oauth2/authorize` with the parameters below.
4. On the callback, check that `state` is the one you sent and that `iss` is
   `https://oauth.mailchimp.com`. Reject the callback if either differs.
5. POST to `/oauth2/token`, form-encoded, with `grant_type=authorization_code`,
   `code`, `redirect_uri`, and the original `code_verifier`. Authenticate with
   HTTP Basic (`client_id:client_secret`). Do this within 60 seconds; the code
   expires after that.

```http
POST https://oauth.mailchimp.com/oauth2/token
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=AUTH_CODE&redirect_uri=REDIRECT_URI&code_verifier=CODE_VERIFIER
```

| Authorize parameter | Required | Value |
| --- | --- | --- |
| `response_type` | Yes | Always `code`. |
| `client_id` | Yes | The `client_id` from registration. |
| `code_challenge` | Yes | `BASE64URL(SHA256(code_verifier))`, no padding. |
| `code_challenge_method` | Yes | Always `S256`. |
| `redirect_uri` | Yes, unless your app has exactly 1 registered | One of your registered redirect URIs. Send the same value to `/oauth2/token`. If you leave it out and your app has more than 1, the user sees an `invalid_request` error page and isn't sent back to your app. |
| `state` | Always send it | A random value you check on the callback, to reject forged callbacks. |
| `scope` | No | Space-delimited scope names. If omitted, you get every registered scope the user is allowed to grant. |

### What comes back

```json
{
  "access_token": "prd_at_9f2c7a1e4b6d4f0a8c3e2b1d9a7f6e5c",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "prd_rt_8b1c0f6e2a4d4f1b9c3e7a5d2f6b8c01",
  "scope": "campaigns:read",
  "account_id": "8d3a3db4d97663a9074efcc16"
}
```

`expires_in` is the access token's lifetime in seconds. `scope` is what the user
approved, which can be less than you requested. `account_id` identifies the
Mailchimp account the user connected.

### Store the connection and make your first call

Key what you store on `account_id`. If the same Mailchimp account authorizes
your app again, update the existing record rather than creating a second one;
otherwise you end up with 2 connections refreshing tokens for one account. For
each connection, store:

- `account_id`
- The refresh token, encrypted at rest
- The access token and when it expires, which you can work out from
  `expires_in`
- The `scope` the user approved

Then call the Marketing API with the access token in the `Authorization`
header. The [API Root endpoint](/marketing/api/root/list) is a good first call:
it describes the account and the role of the user who authorized your app.

```bash
curl https://api.mailchimp.com/3.0/ \
  --header "Authorization: Bearer ACCESS_TOKEN"
```

Use `account_name` from the response to show which account is connected, and
check `role` before you rely on actions a lower
[user level](https://mailchimp.com/help/manage-user-levels-in-your-account/)
can't perform.

## Refresh an access token

Access tokens last 1 hour. To get a new one, exchange the refresh token:

```http
POST https://oauth.mailchimp.com/oauth2/token
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=prd_rt_8b1c0f6e2a4d4f1b9c3e7a5d2f6b8c01
```

The response has the same shape as the code exchange, including a **new**
`refresh_token`, but without `account_id`; keep the one you stored. The refresh
token you sent won't work again, so save the new one before you do anything
else with the response.

- To keep the scopes the user approved, leave out `scope`. To reduce access,
  pass a smaller `scope` on every refresh; Mailchimp doesn't remember it. A
  refresh can't add scopes. See
  [Scopes](/marketing/api-concepts/authentication/oauth-2#scopes).
- Refresh requests don't use PKCE.
- If the refresh fails with `invalid_grant`, the connection has ended. Send the
  user through authorization again.

### Prevent duplicate refreshes

Sending a refresh token twice revokes the whole connection, and the user must
authorize again. It usually happens when 2 workers refresh the same connection
at once. See
[Refresh tokens rotate on every use](/marketing/api-concepts/authentication/oauth-2#refresh-tokens-rotate-on-every-use).

To prevent it, let exactly one function refresh tokens for each connection:

1. Keep tokens in one shared store. Workers, jobs, and API handlers read the
   access token from there and never call `/oauth2/token` themselves.
2. Take a lock for the connection before refreshing: a mutex in a single
   process, a distributed lock across servers. After taking it, read the store
   again; if another caller already refreshed, use the new token and stop.
3. Refresh a few minutes before the access token expires, not after a request
   fails, so refreshes don't start while many requests are in flight.
4. Write the new access token and the new refresh token in one atomic update
   before releasing the lock.
5. If the refresh times out or its response is lost, don't resend the old
   refresh token. Read the store, and if nothing new was saved, ask the user to
   authorize again.

```javascript
const REFRESH_MARGIN_MS = 5 * 60_000; // refresh when less than 5 minutes remain

// store, withLock, and refreshWithMailchimp are your own implementations.
// Pass rejectedToken to force a refresh after the API rejects that token.
async function getAccessToken(connectionId, rejectedToken) {
  const needsRefresh = (t) =>
    t.accessToken === rejectedToken || t.expiresAt - Date.now() <= REFRESH_MARGIN_MS;

  const t = await store.get(connectionId);
  if (!needsRefresh(t)) return t.accessToken;

  return withLock(`refresh:${connectionId}`, async () => {
    const fresh = await store.get(connectionId); // another caller may have refreshed
    if (!needsRefresh(fresh)) return fresh.accessToken;

    const next = await refreshWithMailchimp(fresh.refreshToken);
    await store.save(connectionId, next); // both tokens, one atomic write
    return next.accessToken;
  });
}
```

If the Marketing API returns a `401` for an access token you expected to be
valid, call `getAccessToken(connectionId, rejectedToken)` once to force a
refresh, and retry the call once with the new token. If that fails, send the
user through authorization again.

## Test your integration

Test with a development app and a second Mailchimp account, which is free to
create, so you see the login and consent screens your users see.

Register the development app with a local redirect URI such as
`http://127.0.0.1:3000/oauth/callback`. All of an app's redirect URIs must share
one registrable domain, so a local redirect can't sit on the same app as your
production one.

After your first authorization, make the
[first call](#store-the-connection-and-make-your-first-call) and check that
`account_id` in the API Root response matches the one from the token response.

Then work through the cases your users will hit:

| Case | How to trigger it | What your app should do |
| --- | --- | --- |
| User denies access | Deny access on the consent screen. | The callback has an `error` parameter and no `code`. Show the user a message, and don't call `/oauth2/token`. |
| User approves fewer scopes | Deselect scopes on the consent screen. | Read `scope` from the token response, and turn off features that need what wasn't granted. |
| Same account connects twice | Authorize the same test account a second time. | Update the existing connection for that `account_id` rather than adding a second one. The earlier tokens stop working, so nothing should still be using them. |
| Forged callback | Change the `state` value in the callback URL before loading it. | Reject the callback with a `400`. |
| Callback loaded twice | Reload the callback page after a successful exchange. | Reject it, because its `state` was already used. If a reused `code` does reach `/oauth2/token`, the exchange fails with `invalid_grant`; start authorization again rather than showing a server error. |
| Access token expires | Set `REFRESH_MARGIN_MS` in `getAccessToken` above 1 hour, so every call refreshes. | Save the new refresh token before using the new access token. |
| 2 refreshes at once | Send 2 API requests in parallel for one connection, with `REFRESH_MARGIN_MS` still raised. | The refreshes run one after the other, each sending the newest refresh token, and the connection survives. If both send the same refresh token, Mailchimp revokes the connection; that's the bug the lock in [Prevent duplicate refreshes](#prevent-duplicate-refreshes) prevents. |
| User revokes access in Mailchimp | Revoke your app from **Connected Apps** in the test account. | The next refresh fails with `invalid_grant`. Mark the connection as disconnected and ask the user to authorize again. |
| User's role is too limited | Authorize as a user with a lower [user level](https://mailchimp.com/help/manage-user-levels-in-your-account/), requesting a scope that role can't grant. | Mailchimp refuses the whole authorization and the user stays on Mailchimp's page. If they cancel, the callback has `error=access_denied`. Tell users which permission your app needs before they authorize. |
| User disconnects in your app | Use your app's disconnect control. | Your app calls `/oauth2/revoke` and deletes what it stored for that connection. See [Revoke a token](#revoke-a-token). |

## Change scopes after users connect

To add scopes for a user who has already connected your app, send them through
authorization again. A refresh can't add scopes, so registering new ones
doesn't change existing connections. See
[Scopes](/marketing/api-concepts/authentication/oauth-2#scopes).

1. Add the new scopes to your app on the
   [**Registered Apps page**](https://us1.admin.mailchimp.com/account/oauth2/).
   Until they're registered, requesting them returns `invalid_scope`.
2. Send each user through authorization with every scope you need in `scope`,
   not only the new ones. Ask when the user reaches the feature that needs the
   new access, so they know why you're asking.
3. Exchange the code as usual, then read `scope` from the response. The user
   can decline the new scopes, so keep the feature off if they did.
4. Holding the refresh lock for that connection, replace its stored tokens and
   `scope` with the new ones.

The new authorization replaces the user's existing connection and its earlier
tokens stop working, so save the new tokens before anything else uses the
connection. If a refresh fails with
`invalid_grant` around this time, read the store again before asking the user
to authorize, because the new tokens may already be there.

If Mailchimp has suspended the connection, re-authorization ends with
`error=access_denied` until Mailchimp clears it. See
[Suspended connections](/marketing/api-concepts/authentication/oauth-2#suspended-connections).

## Revoke a token

When a user disconnects your app, revoke their refresh token and delete what you
stored for them:

```http
POST https://oauth.mailchimp.com/oauth2/revoke
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

token=prd_rt_8b1c0f6e2a4d4f1b9c3e7a5d2f6b8c01&token_type_hint=refresh_token
```

Revoking the refresh token ends the connection; see
[Revocation](/marketing/api-concepts/authentication/oauth-2#revocation). You can
revoke only tokens issued to your own app. The endpoint returns `200`
even for an unknown or already-revoked token, per
[RFC 7009](https://datatracker.ietf.org/doc/html/rfc7009), so a `200` doesn't
confirm the token existed.

## Rotate a client secret

Rotate your `client_secret` if it's exposed.

1. Navigate to the [**Registered Apps page**](https://us1.admin.mailchimp.com/account/oauth2/) in your Mailchimp account.
2. Click **Edit** for the registered app you need to update.
3. In the **Client secret** field, click **Rotate**.
4. On the pop-up modal, type **ROTATE** and click **Rotate Client Secret**.

You'll see a modal with the `client_id` and the new `client_secret`.

<Note>
This is the only time you'll be able to see the new `client_secret`, so copy it
and store it securely.
</Note>

Rotation adds a secret rather than replacing one. Your app can hold up to 2
active secrets, and both work at the token endpoint, so deploy the new secret
before you remove the old one and nothing breaks in between.

Once the new secret is deployed, revoke the old one on the
[**Registered Apps page**](https://us1.admin.mailchimp.com/account/oauth2/). You can't revoke an
app's last active secret, and if your app already holds 2 active secrets,
rotation fails until you revoke one.
