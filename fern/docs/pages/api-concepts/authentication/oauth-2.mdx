OAuth 2 lets your application access Marketing API data _on behalf of_ another
Mailchimp user, without ever handling their credentials. It's how third-party
integrations work, and it's a requirement for listing an integration in the
Mailchimp Marketplace.

To implement the flow, see [Set up an OAuth app](/marketing/build/start-developing/set-up-an-oauth-app).

<Note>
This page is for apps whose `client_id` starts with `prd_`, which every app
registered on or after **November 13, 2026** has. If your `client_id` doesn't
start with `prd_`, or your code sends users to `login.mailchimp.com`, see
[Legacy OAuth 2 apps](/marketing/api-concepts/authentication/legacy-oauth-2).
`oauth.mailchimp.com` rejects a legacy `client_id`: the authorize endpoint shows
the user an error page, and the token endpoint returns `401 invalid_client`.
</Note>

## The flow

Mailchimp implements the
[authorization code grant](https://datatracker.ietf.org/doc/html/rfc6749#section-4.1)
with [PKCE](https://datatracker.ietf.org/doc/html/rfc7636). Every endpoint below
is relative to `https://oauth.mailchimp.com`.

1. Your application generates a PKCE `code_verifier`, keeps it on your server,
   and redirects the user to `/oauth2/authorize` with its `S256` hash.
2. The user logs in to Mailchimp and approves the scopes you asked for.
3. Mailchimp redirects the user back to your `redirect_uri` with `code`,
   `state`, and `iss` query parameters.
4. Your application checks that `state` is the value it sent and that `iss` is
   `https://oauth.mailchimp.com`, then exchanges the `code` and the original
   `code_verifier` for tokens at `/oauth2/token`.
5. Your application calls the Marketing API with the access token. When it
   expires, your application uses its refresh token to get a new one.

The token response includes `account_id`, which identifies the Mailchimp account
the user connected. Your application persists one refresh token per connected
account, keyed on `account_id`. Access tokens last 1 hour, so a short-lived
server-side cache or memory is enough for them.

Send PKCE with every authorization request. Your `client_secret` doesn't
replace it: the `code_verifier` proves that the server exchanging the code is
the one that started the flow. Use the `S256`
method; Mailchimp rejects `plain` with `invalid_request`.

Reject any callback whose `iss` isn't `https://oauth.mailchimp.com`. The check
matters most if your app connects to more than one OAuth provider, where it
stops a code from one provider being replayed against another.

## Scopes

Scopes limit what an access token can do. Each scope names one kind of access,
such as `campaigns:read`, and the [API reference](/marketing/api) lists the
scopes each endpoint requires. Scopes are set and checked at each stage:

- **Registration.** You list the most your app can ever request. Asking for
  anything outside that list returns `invalid_scope`.
- **Authorization.** You request scopes in the space-delimited `scope`
  parameter. If you omit it, you get every scope your app is registered for
  that the user is allowed to grant.
- **Consent.** The consent screen lists every scope you request, and the user
  can approve fewer. The `scope` field in the token response is what they
  approved, so read it rather than assuming.

If any scope you request is beyond the user's role, Mailchimp refuses the whole
request at the consent step. The user stays on Mailchimp's page, and your app
isn't redirected or told why. If the user cancels, your callback gets
`error=access_denied`; if they leave, your app hears nothing. Ask only for
scopes the users you expect can grant, and tell users which permission your app
needs before you send them to authorize.

A token can only do what both its scopes and the authorizing user's
[role](/marketing/api-concepts/authentication#user-access-and-revocation) allow.

A connection's scopes are set when the user authorizes. A refresh can narrow
them for the access token it returns, but never add to them, so asking for more
access means sending the user through authorization again. See
[Change scopes after users connect](/marketing/build/start-developing/set-up-an-oauth-app#change-scopes-after-users-connect).

If you remove a scope from your app's registration, existing tokens aren't
revoked, but Mailchimp stops honoring that scope and no longer offers it on new
authorizations. Adding it back restores it for connections that still hold it.

## Tokens and lifetimes

| Token | Lifetime |
| --- | --- |
| Authorization code | 60 seconds, single use |
| Access token | 1 hour |
| Refresh token | 30 days without use. Each refresh returns a new refresh token and restarts the 30 days. |

A connection stays alive as long as your app refreshes it at least once every
30 days. If it goes 30 days without a refresh, the refresh token fails with
`invalid_grant` and the user must authorize your app again.

### Refresh tokens rotate on every use

Each refresh returns a new refresh token and invalidates the one you sent. If
Mailchimp later sees the old one again, it assumes the token was stolen and
revokes the connection: the whole chain of refresh tokens is revoked, every
access token issued from it stops working, and the user must authorize your app
again.

The usual cause is 2 workers refreshing the same connection at once: both send
the same refresh token, the first succeeds, and the second looks like a replay.
A retry after a timeout does the same thing. To avoid it, route every refresh
for a connection through one place that holds a lock.
[Set up an OAuth app](/marketing/build/start-developing/set-up-an-oauth-app#prevent-duplicate-refreshes)
shows the pattern.

### Revocation

A connection ends when any of the following happens:

- Your app revokes a token at `/oauth2/revoke`. Revoking a refresh token
  revokes its whole chain and every access token issued from it. Revoking an
  access token revokes only that token.
- The user revokes your app's access from **Connected Apps** in their
  Mailchimp account.
- The user authorizes your app again for the same account. The new connection
  replaces the old one, and the earlier access and refresh tokens stop working.
- The user is removed from the Mailchimp account.
- The refresh token goes 30 days without use, or is replayed.

When a user disconnects or uninstalls your application, revoke their refresh
token and delete what you stored for them, along with any syncing configuration
tied to that connection.

### Suspended connections

Mailchimp can suspend a connection, and your app isn't told why. While it's
suspended:

- Refreshing fails with `invalid_grant`.
- API calls reject the access token. An API that caches token checks may accept
  it briefly.
- Authorizing again ends with `error=access_denied` on your callback, after the
  user approves.

Only Mailchimp can clear a suspension; the user can't from **Connected Apps**.
If Mailchimp lifts it, the existing tokens work again. If Mailchimp revokes the
connection instead, the user must authorize your app again.

## Your application's credentials

Registering an app gives you its credentials:

- A `client_id` that starts with `prd_`. It identifies your app and appears in
  the authorize URL, so it isn't secret.
- A `client_secret`, which authenticates your app at the token and revoke
  endpoints with HTTP Basic auth.

The `client_secret` has to stay on a server you control, so a mobile or desktop
app needs a backend that makes its token requests and holds its refresh tokens.

## Security practices

- Keep `client_secret` and refresh tokens on your server. Never put them in
  browser code, a mobile app, a desktop binary, or a public repository.
- Don't log credentials or tokens, or send them in URLs, query strings,
  analytics events, or error reports.
- Register a separate app for development, staging, and production, so a leak
  in one environment doesn't expose the others.
- Store refresh tokens server-side, encrypted at rest, one per connected
  account. Limit access to them to the service that performs refreshes.
- Keep access tokens in memory or a short-lived server-side cache, never in
  `localStorage` or cookies readable by scripts. Send them only in the
  `Authorization: Bearer` header, over HTTPS.
- Request only the scopes your app needs. Users see the list and can decline.
- Don't skip `state`, PKCE, or the `iss` check, and don't turn off TLS
  verification, even in a demo.

## Errors

The OAuth endpoints return errors in the
[RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749#section-5.2) format: a
JSON body with `error` and `error_description`.

During authorization, an error arrives as an `error` query parameter on your
redirect URI, along with `state` and `iss`. The exception is a request Mailchimp
can't safely redirect, such as a legacy `client_id`, or a missing
`redirect_uri` when your app has more than 1 registered. Mailchimp then shows
the user an error page and never sends them back to your app.

| Error | Cause | What to do |
| --- | --- | --- |
| `access_denied` | The user denied consent, cancelled after Mailchimp refused a scope beyond their role, or the connection is [suspended](#suspended-connections). Arrives on your redirect URI. | Show the user a message, and don't call `/oauth2/token`. |
| `invalid_request` | `code_challenge` or `code_challenge_method` is missing, or the method isn't `S256`. On the authorize endpoint, also a missing `redirect_uri` when your app has more than 1 registered. | Send both PKCE parameters, with `code_challenge_method=S256`, and always send `redirect_uri`. |
| `invalid_scope` | A requested scope doesn't exist or isn't in your app's registration, or a refresh asked for more scopes than were approved. | Request only registered scopes. On refresh, request the same scopes or fewer. |
| `invalid_grant` | The code expired or was already used, the `code_verifier` doesn't match, the refresh token is expired, revoked, or replayed, or the connection is [suspended](#suspended-connections). | Send the user through authorization again. Don't retry with the same code or refresh token. |
| `invalid_client` (401) | Wrong `client_id` or `client_secret`, a revoked secret, or a legacy `client_id`. | Check the credentials your server sends. A legacy app uses the [legacy flow](/marketing/api-concepts/authentication/legacy-oauth-2). |
| `unauthorized_client` | A grant type other than `authorization_code` or `refresh_token`. | Use one of those 2 grant types. |

## Standards

The flow follows these specifications.

| Specification | What it covers here |
| --- | --- |
| [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749) | The authorization code grant, and the error format |
| [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636) | PKCE. Only the `S256` method is accepted. |
| [RFC 9207](https://datatracker.ietf.org/doc/html/rfc9207) | The `iss` parameter on the callback |
| [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700) | OAuth 2.0 Security Best Current Practice: PKCE for every client, and refresh token rotation with replay detection ([§4.14](https://datatracker.ietf.org/doc/html/rfc9700#section-4.14)) |
| [RFC 7009](https://datatracker.ietf.org/doc/html/rfc7009) | Token revocation |
